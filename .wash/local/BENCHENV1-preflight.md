## BENCHENV1: rootless Podman in a default-confined TCG VM (read-only feasibility, 2026-10-04)

Scope: source/docs and local executable inventory only; no VM/image/container launch, no retry of the stopped `redoubt-bench-env-preflight`, and no source, host policy, or permission change. The previous `newuidmap` failure still blocks the real OpenSSH reference gate. This is **a conditional design for Architect review, not a verified equivalent environment or an acceptance result**.

The bench currently executes `sg <bench-group> -c 'podman --cgroup-manager=cgroupfs ...'` (`tools/testbench/src/ssh.rs:202-209`). It uses `image exists`, then `build -q -t <digest-derived-tag> -f <absolute Containerfile> <context>` (`ssh.rs:212-254`), then one `run -i --rm --network=none --pull=never` per SSH session with exactly four absolute host-file bind mounts (three `ro,z`, one writable `z`) and the real pinned image/`sshd -i` (`ssh.rs:255-270,324`). It reads the log to confirm the OpenSSH version. Official Podman 5.4.2 documents `CONTAINER_HOST`/SSH remote mode and the rootless Unix service socket, and documents `image exists`, `build`, and `run` command forms. It also says that **bind-mount source paths in remote mode are on the server**, and that most global flags, including `--cgroup-manager`, do not configure the remote server. Thus environment-only `CONTAINER_HOST=ssh://<guest-user>@127.0.0.1:<forwarded-port>/run/user/<guest-uid>/podman/podman.sock` could route the unchanged CLI only if `sg` preserves the environment, the remote client accepts this exact `-f`/context invocation, and the guest supplies *the same absolute paths* for the recipe, build context, and each dynamically created case file. `image exists` would query the guest's storage; the pinned image must be built there. These command/path behaviors require focused validation; documentation alone does not prove the exact runner works remotely. Configure cgroupfs in the guest service/storage environment; the client's flag is ineffective remotely.

Do **not** expose the Podman API on TCP, even localhost: Podman warns that it grants arbitrary execution as the service user and recommends SSH forwarding to the Unix socket. A candidate transport is QEMU user networking with a port forwarded on the **outer test container's** `127.0.0.1` to guest SSH, and an SSH identity restricted to the guest bench account. The Podman service remains rootless under that guest account, with verified uid/gid maps so uid 0 in reference containers maps to the guest bench user outside them. The forwarded endpoint and key still grant that account's authority to the holder; protect them as bench credentials. `--network=none` applies to each reference container; it does not disable the separate client-to-VM control channel or the guest build's required registry/network access. The pinned Debian/OpenSSH Containerfile, digest, package version, per-file modes, and server-version probe must stay unchanged.

Guest prerequisites: bootable amd64 Linux kernel/rootfs with user namespaces and subordinate-ID helpers enabled *inside the guest*; Podman remote service and client of compatible versions, `newuidmap`/`newgidmap`, subuid/subgid ranges, rootless OCI runtime and vfs or other tested rootless storage, guest cgroupfs configuration/cgroup delegation as required, and SSH server; registry access for the one pinned build. Outer container prerequisites: `qemu-system-x86_64` with TCG, an image/kernel/initramfs, sufficient disk/RAM/CPU and working user-mode networking/localhost host-forward, plus the normal Rust/testbench and RISC-V QEMU toolchain for the full bench. The current `Dockerfile` installs `qemu-system-riscv`, not x86 system QEMU; the host probe `command -v qemu-system-x86_64` returned no path, and the bounded file inventory found no qcow2, vmlinuz, initrd, or `.img` under `.wash`, `tests`, or `tools`. No guest image or boot arrangement is prepared. TCG needs no `/dev/kvm`, but the ability to boot this VM under default confinement has **not** been tested. The full bench should run in the outer test environment and send only the OpenSSH reference commands to the guest, so Redoubt's RISC-V product-QEMU is not nested inside the TCG VM; running both QEMU processes may still increase load.

The decisive unproven item is safe path sharing. QEMU's documented unprivileged 9p `local` backend cannot use `security_model=passthrough` without root; `mapped-xattr` stores guest UID/GID/mode/symlink attributes in host xattrs, while `mapped-file` adds hidden metadata files and QEMU warns that ordinary Unix tools cannot interact with that export. A limited export mounted at the same guest absolute path could in principle cover the immutable reference recipe/context read-only and the dynamic case-directory subtree writable, but it must preserve the bench's per-file `ro,z`/`z` behavior, host-visible log writes, correct ownership, symlinks, xattrs/SELinux relabeling, and concurrent file operations. Exporting the whole project writable would give the guest bench account broad worktree authority and is not the proposed boundary. The fact that QEMU itself would run as outer `dev` limits host file access to that account but does not establish safe semantics or label compatibility. A remote `-v` cannot consume a local case path absent from the guest. These are **validation gates**, not assumed capabilities.

Architect review candidate: (1) approve only an isolated guest-image/TCG preparation, default-confined outer container, localhost SSH-forwarded guest Unix socket, and narrow read-only recipe plus writable case-output exports; (2) verify guest rootless UID/GID map and its effective outside identity, `sg`/`CONTAINER_HOST` inheritance, exact remote `image exists`/`build -f`/`run -i` behavior and cgroup settings with no changed runner; (3) verify four per-file mounts, `:z` handling, writable log, networkless session, pinned build and server-version probe; (4) only then run `cargo testbench bench-ssh-loopback-openssh`, and later the normal whole bench outside the VM. Any failure of identical path/mount/label semantics makes this approach a **no-go for the unchanged bench** and calls for an owning-rule/runner change and review, not a gate skip. At present, there is no ready runnable setup and the gate remains missing.
