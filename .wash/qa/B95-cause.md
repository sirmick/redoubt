> Cause (detail .wash/local/B95-identification.md, reproduced both widths with an injected 11 s fill, logs .tmp/B95/inject-*): not walfsd's write path or blkd (no poison line; IPD2's is B51's poisoning, a different path). libs/rt ninep_mux.rs pump sets a session's deadline = now+bound with `now` read BEFORE fill serves the pending requests synchronously; a fill >=10 s (walfsd's bound = COLLECT_WAIT) leaves the deadline past at the answer, expire ends the session, the waiter's next call opens a fresh one (OPENED), the hub takes that as the connection's end: every later op of the VM is eio (B93's first run already printed cleaned: [] and 1 waiters). The stranded fresh session (no call parked) outlives the VM up to 10 s; init restarts beamlet with the same manifest badge, so the replay's Hub::connect lands on it, gets [0,0,0,0] not OPENED, Unexpected -> eio. The module comment says a session lasts the bound 'since the last one returned': the code departs from it.
> 
> Options (Tier A, libs/rt or libs/client):
> (1) Recommended: pump sets the deadline from time_now() after the answer is sent (a pending request's TIMEOUT judged then too). Smallest; matches the stated rule. Sweep every bin linking redoubt_rt.
> (2) also: a waiter that gets OPENED disconnects that fresh session, so none outlives its VM and a same-badge restart opens cleanly.
> (3) hub recovers from OPENED (outstanding Ended, connection kept). Larger change; I'd not.
> A natural load repro (needs the orchestrator's go) tells (a) one >=10 s fill from (b) a waiter not re-calling within 10 s; (1) fixes (a) only, (2) contains both to one VM.
> 
> Q2: the replay runs inside the grace in every passing run. Options: (a) leave it, the fix makes the replay clean; (b) the case's manifest stops init restarting beamlet; (c) a bench feature ending a case at its last expect. Recommend (a), testbench.md unchanged. Your call on both.

> P2: fresh requests are served, never timed out; B95 folds it. A request's deadline is the bound on a request the file server asked to hold (serving.md: a Read::Wait "is answered Rerror timeout at the server's deadline for it"); it is not a clock on the server's own time, which the client is told it has no clock on ("a late answer is a busy server"). So a request that has not been tried is tried once whatever the clock says, in order; only a request that was tried and is waiting is judged against its deadline, and that judgment is made at the time it is made, as ruling 1 says for the session. A fill that takes 11 s for one request may not turn its untried siblings into timeouts. mux_held gets the assertion: two requests in one fill, the first slow past the bound, the second answered with its data.
