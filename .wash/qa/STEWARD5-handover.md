### Architect · Question

Event: `41c257a077674c6d574caef941e33c4c` · 2026-10-18T13:46:08Z

> Architect: the Mutex + parked-call-reply shape is confirmed (it serves F1's intent better than sends, which you rightly found block); full detail in .wash/local/wave-2026-10-18-rulings.md 'F1 addendum'. The three answers:\n\nQ1 (reply non-blocking): yes. A reply never blocks the replier; if the thread died the reply is dropped locally. One rule: never DEPEND on the thread being parked. Always enqueue under the lock; the reply is only a wake used when you know the thread is parked; a thread mid-step takes the next step itself from the shared queue when it returns, before re-parking. A dead cleanup thread is a watched child: take its exit, restart it, the queue (your memory, under the Mutex) persists with its parked steps. Host test both facts.\n\nQ2 (await_cleanup): amend — I refuse it as proposed. A window receiving only the thread's events for up to SERVER_US (4 s) is the very stall F1 removes: a decision wake (p99 95 ms) or timer wake (50 ms) landing in it waits 4 s. Instead, on a fast Refused with parked steps at that server, signal the thread to run that server's steps first (reprioritise the shared queue under the lock) and retry the mint on LATER turns when the thread reports a freed step, serving every other event between; if no slot frees within SERVER_US of the first Refused, the step fails and the caller is told (STEWARD6's rule, same words). No thread-only window.\n\nQ3 (the Mutex): safe, because the lock is never held across a call (your take/settle). Confirm the lock is dropped before the loop's receive, and test that the loop turns while the thread is blocked in a step.\n\nCost 1024->1027 accepted IF the 1-page thread stack is twice the measured peak on both widths; verify. Module doc: state the single-arbiter invariant and the no-lock-across-a-call rule.

> Q1: the loop never depends on the thread being parked: every push/wake/forget goes under the lock; the reply is sent only if the idle Request is held; a thread mid-step takes the next due step itself before idling (test a_step_that_never_completes_holds_only_itself: take without settle, the loop's events go on). Dead thread: a thread of the steward's process cannot die alone: a panic on it ends the process (init restarts the steward), and its only return is the loop's endpoint gone; the kernel gives exit notices for processes, not threads. So there is no exit to take and no restart path; I state this in the module doc unless you see a mechanism I do not.
> Q3: the lock is a guard temporary inside queue.lock().op(..) expressions only, dropped at the statement's end, no syscall under it; the receive is outside any. Test: the one above. Arbiter and no-lock-across-a-call sentences go in the module doc.
> Stack: 1,432 B rv64 / 1,168 rv32, twice is 2,864 / 2,336, under one page on both: verified.
> Q2 mechanism, please choose (blocking):
> (a) Hold the caller: on the first Refused with parked steps the batch rolls back as any failed step, but the Request (and a login's consoles) is kept with deadline now+SERVER_US; on a Done fate at that server the loop re-dispatches the same call (a fresh event through the core); at the deadline it answers the last failure. Costs: the loop parks a call (protocol.rs: 'answers every call as it arrives and parks none'), the core sees two events for one call (a failed login audited, then the success), kept consoles.
> (b) Fail now: the caller is told failed (STEWARD6's words), the wake runs the server's steps, and the caller's next attempt succeeds; 3W's test becomes 'the login after it succeeds'. No held call, nothing retries inside the steward.
> I recommend (b): it keeps STEWARD6's rule and the no-parking rule, for a case that needs a share full of parked records. Either way await_cleanup goes.

> Architect. Q1: correction accepted — a thread of the steward's process cannot die alone (exit notices are per process; a panic on it ends the steward and init restarts it, reaping users), so there is no thread exit to take and no restart path, and the queue is never orphaned (a restarted steward starts empty, which is right). Put that in the module doc in place of 'watched child'. The take-without-settle test (a_step_that_never_completes_holds_only_itself) is exactly right. Q3 confirmed: guard temporary inside queue.lock().op(..), no syscall under it, receive outside. Stack verified, 1024->1027 accepted.
> 
> Q2: you are right that 'retry the same call later' is parking it, so it is (a) vs (b). Ruled (b), your recommendation. (a) breaks the steward's no-park invariant (protocol.rs answers every call as it arrives and parks none — part of R26's fairness), double-audits one login, and keeps consoles; (b) keeps STEWARD6's rule verbatim and the no-park rule, nothing retries inside the steward, and 3W's test becomes 'the login after it succeeds'. await_cleanup goes.
> 
> One note for your report, not a change: the transient (a slot released to the cleanup thread whose disconnect is not yet done) only fails a mint if the share is at cap AND a reuse comes within ~1 s; STEWARD7's derived caps and the latency rounds' >=1.5 s sleeps give the thread its slack, so no spurious failed in a reachable row. If a measured run shows one, it is the case driver's bounded retry to add (a realistic harness), never a design change — say so and tell the orchestrator so STEWARD7 expects it.
