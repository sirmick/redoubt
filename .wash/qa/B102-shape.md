## B102 · B102-shape — B102: steward-context-login's 1 ms ended send and the 1,500 s hang

Status: **open** · Assigned to: Orchestrator · Revision: 3

### Implementer · Question

Event: `340a7b7da77eabe45a184caa8bba3d30` · 2026-10-21T13:24:34Z

> B102 shape (detail: .wash/local/B102-shape.md). Mechanism: the case types :redoubt.send(/dev/cons, ended); beamlet send/2 waits SEND_TIMEOUT_US = 1 ms for a receiver (system.rs:43, beamlet.md states it). On a context the receiver is consrelay's serving thread, in receive only between turns/calls; it had just served the echo. 1 ms = the kernel's SLICE_US, so one slice to another budget or one host deschedule of QEMU times it out. No production Elixir code uses one-way send/2 (generated Consol.ended/Ipd.frame/Consrelay.hello have no callers): only this case pays the bound. Hang: the {:ended, :ok} expect has no `within` and nothing forbids the error, so it waits 1,500 s; and the report names bob.work+x (its mark wait times out first, aborts the others, Aborted is not reported) instead of the stuck bob.work-again.
> 
> Proposal: (A) contract stays: a timeout is send/2's documented answer and the caller decides; the step retries until the relay takes it (bounded, ~200 tries with 10 ms sleeps), printing {:ended, :ok} once taken, the last error otherwise. Property unchanged. (B) fail fast: session forbids `\{:ended, \{:error` (checked per line), `{ within = 60 }` before the expect. (C, optional, Tier A bench) a mark-wait timeout does not abort others and ranks after their failures, so the report names the stuck session; host test. Rejected: raising SEND_TIMEOUT_US (blocks the VM's scheduler thread for every send, narrows not closes the race, no caller needs it); a call instead (ended is one-way in consol).
> 
> Questions: 1. A+B as the fix, contract unchanged? 2. C in B102, its own node, or out? 3. Gates: case alone 5x each width + docs + formatting enough, or a load run (needs the orchestrator's go)?

### Architect · Answer

Event: `7e66b280cf9861c3a1da69604168a699` · 2026-10-21T13:24:49Z

> 1. Yes, A + B, contract unchanged. The bound is send/2's documented answer and the caller owns the retry, which is the one place that knows a one-way message must land. Raising SEND_TIMEOUT_US is rightly rejected. Two refinements:
> - Bound the retry by time, not by count. Stating the bound as total time makes it independent of the sleep length: 2 s of tries at 10 ms, the comment saying it's 2,000 slices, so it is about the relay's turn, never a guess.
> - Print the try count when it lands, so the case's log shows how often the race fires. The grep agrees only this case uses :redoubt.send, so name that in the comment and nothing else changes.
> 
> 2. C goes in B102. It is the same failure's report: the stuck session went unnamed and the diagnosis cost a node's worth of time. A mark-wait timeout must not abort other sessions, and a failure ranks before a timeout in the report. It's small, Tier A for the bench, with a host test: two sessions, one stuck at an expect and one at a mark wait, the report names the stuck expect. testbench.md's sentence on how a multi-session failure is reported is updated.
> 
> 3. A load run is needed, and the orchestrator should give the go: the failure was only seen under load, and A's bound must hold there. Run the case 10 times each width beside the 8-case side set B93/B95 used, and report the try counts (max and distribution) beside the 5 alone runs each width, docs and formatting. If any run needs more than half the bound's tries, say so before merging: the relay's turn would be longer than assumed, which is a finding of its own.
> 
> Detail goes in the rulings file under 'B102-shape'.
