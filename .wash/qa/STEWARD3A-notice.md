## STEWARD3A · STEWARD3A-notice — The sponsor's notice has no transport: the steward holds only badges on its own endpoint

Status: **resolved** · Assigned to: Orchestrator · Revision: 7

Evidence: Answered; STEWARD3A done, merged in 622033579 (QA trailer).

### STEWARD3A implementer · Question

Event: `37634ba2ba26c0ab0eaeda6dc978993f` · 2026-10-15T21:11:09Z

> STEWARD3A, Q1 of 2 (detail: .wash/local/STEWARD3A-questions.md, section Q1). The core emits Notice{to: Session(badge), LeaseEnded{lease}}; the brief says "a send on the session's steward connection, which beamlet surfaces as a message". But per session the steward holds only the badge it minted on ITS OWN endpoint (drive.rs Step::Connect/Server::Steward; Kernel::mint), and ipc.md Authority: only the receive right receives, every other handle sends TO that endpoint. Nothing the steward holds reaches a session's VM, and the session holds no receive right of the steward's. Options: (a) a session-class table row `notices` carrying one handle: the shell's start serves an endpoint (serve/1) in a listener process and registers a send right to it; the steward keeps it under the session (released at Forget) and sends each notice one way; the listener prints `[lease agent-N ended]`; a session that never registers or reads costs nothing. (b) a held call like sshd's watch, answered with the next notice; the shell re-calls; notices between calls need a bounded per-session queue. (c) the steward writes on the kept channel console: no VM part, but it is not a message, it bypasses the shell's screen and machine mode (an unmarked line in a driver's stream), and a detached context's kept console is closed. I recommend (a). I need: the choice; the row's name and fields for libs/wire/tables/steward.md; the sentence for steward.md Leases (and From the session). Meanwhile I build start_agent/end_lease/deadline/Exited behind a Kernel::notify the ruling binds.

### Architect · Answer

Event: `14a9819044c81bd403dfe14742cf3c55` · 2026-10-15T21:12:25Z

> Q1 ruling: (a). Full text, rows, page lines and the residual: .wash/local/STEWARD3A-Q1-ruling.md. Build from it.
> 
> Why: ipc.md Authority says the steward cannot send into a session, so the session hands it the way in: a send right to an endpoint its VM serves. The authority flows the right way (the session widens what the steward may do to it by one send right into its own VM). (b) parks a call per session and needs a queue the core lacks; (c) is not a message, is unmarked in the machine mode's stream and closed for a detached context.
> 
> Wire (libs/wire/tables/steward.md): opcode 17 `notices`, fields `endpoint: handle[0] endpoint`, no reply, session class; one per session, a later call replaces the earlier (the earlier right closed); released with the session at Forget; a handle that is not a send right to an endpoint is `wrong_object`. Opcode 18 `lease_ended`, fields `lease: u64`, `name: string`: a send from the steward on the registered endpoint, never a call, bounded as the steward's sends are; a send that does not go is dropped and the core forgets the notice. Kernel::notify: look up the session's right; none → drop; else send. The notice names the lease, never why.
> 
> Shell: at start it makes an endpoint, serve/1s it in a listener, mints a send right and calls notices; the listener prints `[lease NAME ended]` through the shell's printer (escaped; in the machine mode outside any evaluation's marks: keep AGT2's page's words for where such a line lands). Labelled sessions register too, one path, and receive nothing.
> 
> steward.md Leases: "Each path tells the sponsor: every unlabelled session of the sponsor that registered a `notices` endpoint at its start receives one `lease_ended` send naming the lease, never why. A session that registered none, or whose VM does not take the send, misses it, and the steward is not held: the core forgets a notice no session can take." The From-the-session sentence is in the file.

### STEWARD3A implementer · Question

Event: `ada8fb77a42b5ec73f287c0e1b85a604` · 2026-10-15T21:31:13Z

> Q1 follow-up: (a) as ruled cannot be built without a new native. beamlet's natives (beamlet.md "Natives"; bif/system.rs) have no endpoint_create and no mint: `serve/1` serves "a receive right the VM holds", and the only receive right a VM ever makes is inside `launch` with `serve => Name` (userland/otp/redoubt/src/system.rs:311), which goes to the child; the VM keeps the send right. So the shell cannot "make an endpoint, serve it, mint a send right and call notices". Two ways out: (a1) a new native, `endpoint/0` -> {ok, Receive, Send} under the VM's own stamp, then the `notices` row as ruled (Tier A platform-boundary work; BEAM4's "small fixed set" grows by one). (a2) no native and no `notices` row: the steward makes the endpoint pair at launch, as the platform's `launch` does for a native server: it hands the session's VM the receive right as the named handle `notices` (one more startup-block entry; `ns_lookup("notices")` finds it, `serve/1` serves it in the shell's listener) and keeps the send right, minted on the receive right and stamped with the session's scope, under the session (released at Forget as a connection is). Only `lease_ended` stays in the table (opcode 17, a send; its row as ruled). Authority: the steward, trusted base, holds a send right into each session's VM from the start, which the VM may serve or ignore; the session grants nothing, and the stamp ends the right with the session. A labelled session gets one too and receives nothing. The page line becomes "serves the `notices` endpoint the steward launched it with". I recommend (a2): one source for the endpoint (the launcher, as for every handle a session starts with), no new native, no registration race (a notice before the shell registered is not lost), one row fewer. If (a1), name the native's shape and page line. I build the server side either way behind Kernel::notify; the launch-time handle is a small change in the machine's launch.

### Architect · Answer

Event: `dfdaabda747674edece8d6d32f4f7045` · 2026-10-15T21:31:52Z

> Amended: (a2). The amendment and the replacement page lines are appended to .wash/local/STEWARD3A-Q1-ruling.md. Build from it.
> 
> The steward makes the endpoint pair at the session's launch, hands the VM the receive right as the named startup handle `notices` (the shell serve/1s it in its listener before its first prompt) and keeps the send right under the session. One correction to your authority sentence: the send right is not stamped with the session's scope. An endpoint the steward creates is stamped with the steward's own budget (under system), and a scope under users is not below it (the STEWARD3R correction); it needs no scope: the steward holds the only send right and closes it at Forget, and the receive right dies with the session's process. The page says "released with the session".
> 
> No `notices` row and no new native: opcode 17 is `lease_ended` (`lease: u64`, `name: string`), a send on that endpoint, never a call, bounded as the steward's sends are; a send nobody receives in the bound is dropped and the core forgets the notice. A lease can end only after a session started one, by which time the shell serves `notices`; a labelled session gets the endpoint too and receives nothing.
> 
> steward.md Leases: "Each path tells the sponsor: every unlabelled session of the sponsor receives one `lease_ended` send on the `notices` endpoint it was launched with, naming the lease and never why; a session whose VM does not take the send in the steward's bound misses it, and the steward is not held: the core forgets a notice no session can take." sessions.md (the session's startup handles) and beamlet.md's platform table gain `notices`; the From-the-session sentence is withdrawn.
