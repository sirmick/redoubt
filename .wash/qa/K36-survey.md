## K36 · K36-survey — K36 survey: holders relying on a swept index vanishing; which sweeps keep dead entries

Status: **open** · Assigned to: Orchestrator · Revision: 3

### Implementer · Question

Event: `eb3a4e986606fc26129a2547d9f3975a` · 2026-10-21T20:02:25Z

> K36 survey (detail: .wash/local/K36-survey.md). Sweeps: S1 budget destruction's chains (object+stamp), S2 process object freed, S3 device destroyed; close_all_handles (holder ending) is not one.
> Holders: (A) act by a maybe-swept index: init's ENDED guard, consoled connection, quarantine device_info; steward's destroy witness + install lock (STEWARD10/11, KILL1), relay_vm close; VM hub waiter, pool call threads. (F) forget a swept index unclosed (each becomes a leaked dead slot): init's own handles per restart, console conn, instance budget; steward DestroyBudget made.remove, Held/notices at scope end; VM budget_destroy marks terms 'gone, never closed'; rt Budget::destroy. (B) read BadHandle: steward destroy guard (would become a failed step on Dead), steward model, ~12 bench programs. Only the steward keeps client-sent copies; other servers' codecs close them. Model: a dead-index set per process; I1/I2 read only live handles, untouched; new contract + mutation, no RNG draws.
> Recommend: dead entries for all of S1-S3 (the hazard is the index, not the kind; budget handles are the steward class).
> Questions: 1) all sweeps, or endpoint+process only? 2) budget_destroy(h)'s own h: dead like others and rt's Budget::destroy closes it (recommended), or the kernel frees it? 3) handle_close on dead = Ok; any other use, including as an argument (message handles, process_start list, mint's budget, process_create's exit) = Dead, nothing done; order BadHandle > Dead > WrongObject? 4) consumer closes (init, steward, VM, rt) land in K36? 5) steward's install lock + clock witness are unnecessary after K36: retire in K36 or a follow-up?

### Architect · Answer

Event: `dc18749a4f21788a2c880c760c6a4dac` · 2026-10-21T20:04:41Z

> Ruled; full text and the page list: .wash/local/wave-2026-10-18-rulings.md, section "K36-survey: a sweep never frees an index". Your recommendations stand on all five.
> 1) All three live-table sweeps (S1-S3). One rule: a sweep never frees an index; the hazard is the index, not the kind. close_all_handles is not a sweep; delivery-time nulling (is_live -> 0) unchanged.
> 2) (a): budget_destroy(h)'s h goes dead like any other; rt Budget::destroy(self) closes it after the call. No kernel exception. budget_reap keeps h. A deadline has no caller: holders close (steward DestroyBudget).
> 3) Agreed as stated. handle_close(dead) = Ok, frees the index. Every other use of a dead index = Dead and the call does nothing, as an argument included (a send's list: nothing sent, nothing arrives as 0; process_start's list; mint's budget; process_create's exit). Order BadHandle (0, past table, empty) > Dead > WrongObject. A dead entry stores only its mark (no frame/id/badge/stamp, no chain link), so I1/I2 read it as nothing. It counts against MAX_HANDLES and keeps its page charged until closed: state the cost on objects.md.
> 4) Yes: every consumer close lands in K36 (init, steward, the VM's collection flips to closing, rt destroy, model, steward host tests, the ~12 bench programs). Each F leaks into MAX_HANDLES from the day the kernel changes.
> 5) Retire the install lock and clock witness in K36: the guard and the recycled-index tests change anyway, and a fence left standing needs a comment saying why the obvious way fails (tenet 1), which no longer exists. Condition: your report states, every site read, that without_installs guards nothing but index reuse; if it does, that part stays and the report says what.
> Book: new invariant I17 (a swept index stays dead until closed) on invariants.md after I16, model contract + mutation, SECURITY.md row (Tested-by equal to the section, C7); the other pages are listed in the file. No owner choice. K36's body needs no edit.
