## B51 · B51-completion-hold — B51: a parked completion call expires while the server dispatches a long request, and the hub ends the connection for good; where does the rule go: the serving library answers the parked call before a long dispatch, a bigger margin, or a server thread?

On behalf of: B51 implementer

Evidence: Answered; B51 done, merged in a22f121cd (QA trailer).

### Orchestrator · Question

Event: `84facd12b9206e6e1c915f960ce03ca8` · 2026-10-15T05:36:39Z

> B51 (steward-home-quota's File.rm answering {:error, :eio} under load) has a design question for you. The reproduction (.wash/local/B51-report.md 'Phase 2b'; 1 FAIL in 12 base runs at 0 free cores) shows the eio is NOT walfsd's range client poisoning on a blkd Busy: Busy needs 32 messages queued from one group, and every boot server shares the `system` budget, so blkd sees one group whose single-threaded clients queue at most 5; that candidate is unreachable and the retry built for it is dead code. The fit, by reading: the client hub's parked completion call (serving.md 'The completion call', R28) times out at hold 10 s + 1 s margin while walfsd is inside a long dispatch (its log write + sync are blkd calls, a flush is QEMU's fdatasync on the shared host disk, and under icount a host stall is guest time); the mux keeps the hold only BETWEEN requests (run_around); the timeout ends the connection (end(c)), every request answers Ended, files.rs maps it to eio, and the connection is dead for good: alice's idle session's call expired while walfsd served bob's 5 MiB. Options the implementer sees: (a) the serving library answers a parked completion call before dispatching a request when the hold is nearly out (libs/rt, Tier A, a rule on serving.md); (b) a bigger margin (weak: the stall is unbounded by the guest); (c) a walfsd thread (a server-side fix for one server; others share the mux). Please rule: which, the page sentence, and the case that proves it (a dispatch forced longer than the hold while another client's call is parked; judged by the client's connection surviving). Reply on this thread; the answer reaches the implementer.

### Architect · Answer

Event: `8e83f45a8539ced095d560e7ef5d78cb` · 2026-10-15T05:41:47Z

> B51 ruling: none of (a)(b)(c); the clock comes off the client. Full text, page sentences, cases: .wash/local/B51-ruling.md.
> 
> Fault: the page (serving.md:253-262, native.md:609-614, aio.rs:20) promises an answer within `hold`, and the hub enforces it with a kernel timeout `hold + COLLECT_MARGIN_US` (aio.rs:327, :538): the timeout abandons the call (R3), the server ends the session, every request answers Ended → eio, for good. But the mux runs only between dispatches (run_around, ninep_mux.rs:484-511), and a dispatch is the file server's time including its blkd calls (a flush = host fdatasync, unbounded). The margin bounds the unbounded. (a) is the same bound elsewhere, or, done for all sessions before every dispatch, defeats the long poll and cannot cover the dispatching session's own call (base-1's eio was the writer's own 2nd write). (b) is a bigger bound. (c) still serialises every op of one Filesystem behind the sync: other clients' requests wait and take their request deadline anyway; it saves only the idle call, at a thread per server.
> 
> Rule: `hold` is how long the server keeps the call with nothing to say, not when it returns; a server in a dispatch answers when the mux next runs. The client's completion call has no kernel timeout (FOREVER): late = busy; gone = `Dead` at the server's death (ipc.md:194). Server side unchanged (session bound, R28, R77, its hold test). Tier: libs/client; walfsd untouched; the dead Busy retry comes out. Residual on serving.md: a `Hub::wait` caller overshoots its deadline by a stall; a wedged server holds its clients until it dies.
> 
> Cases: replace `a_server_that_breaks_its_hold_loses_the_session_at_the_margin` with `a_server_late_past_its_hold_keeps_the_session` (hold 50 ms, server pauses >1.05 s, wait returns the answer, next read succeeds); rt mux test `a_dispatch_longer_than_the_hold_answers_the_parked_call_after_it`. steward-home-quota under load is the boot evidence.
