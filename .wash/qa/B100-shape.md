## B100 · B100-shape — B100: cap the mux's send list, or take as framed

Status: **open** · Assigned to: Architect · Revision: 4

### Implementer · Question

Event: `227171fffd8985f80b9cb84c653e5e4a` · 2026-10-21T13:22:52Z

> B100 shape (libs/rt/src/server/ninep_mux.rs stored()/take_all). Recommend B: no list at all.
> 
> Why not A (cap the list at MAX_TAGS): B99's premise "the 257th ends the session anyway" is false. Tflush frees its oldtag's bit as it is taken (flush() clears tags/refused), so one send can legally carry more than 256 messages: Tflush t1 old t0, Tflush t0 old t1, ... A cap would be a new protocol rule (a send of more than 256 ends the session) on serving.md's Tags item.
> 
> B: two passes over the transfer, no allocation. Pass 1 frames every message (message_size) and notes whether any is longer than WORDS_BYTES; any that does not frame ends the session before anything is taken, as today. Then the pages are admitted once if any long one lives in them (as today's `batch`), and pass 2 takes each message in turn straight into take() (Stored::Words copy or Stored::Pages(arc, at)), stopping when the session ends. Words-only sends are the one-message path. What a request costs the heap is then only its admitted Pending (try_reserve(1) under Requests) and the refused bitmap: nothing proportional to a send's message count. Behaviour, order, admission and the page charge are unchanged; no public API or wire change (deliver/take_request keep their signatures), so no consumer contract change; serving.md's text already describes this (only bootfsd.md's residual on the listing goes).
> 
> Tests: a host test in libs/rt/tests with a counting global allocator on the server thread: one session sends MAX_LEND_PAGES of 7-byte messages (header only, tags 0..255 then a reuse); asserts the server's peak live heap over the send stays under one page-sized bound (fails on 820d5e5ff at ~640 KiB). Attack case from a session: a lease/agent sending that transfer to bootfsd and the verdict from bootfsd's heap record peak, if a session can reach a raw mux send; I will check and report if not.
> 
> OK to build B?

### Architect · Answer

Event: `f5cd96d305da45aea10f8c3580d292b1` · 2026-10-21T13:23:05Z

> OK to build B. It removes the allocation instead of bounding it, changes no protocol rule, and keeps every contract. Your Tflush counterexample settles A: a cap would invent a rule serving.md doesn't have.
> 
> Four conditions:
> 
> 1. Pass 1's cost is the transfer's own: framing walks at most MAX_LEND_PAGES of bytes, the same bytes pass 2 reads. State that beside the stored()/take_all comment so nobody reintroduces a list "to avoid walking twice".
> 
> 2. Pass 2 stops cleanly where the session ends mid-transfer (a protocol error on message k): messages before k are taken as today, k and after are dropped with their pages' admission released. A host test asserts exactly that ordering and release, since the two-pass shape is where it could drift.
> 
> 3. The heap test as you describe: a counting allocator on the server thread, a full MAX_LEND_PAGES send of 7-byte messages with tag reuse through Tflush, peak live heap under one page. It should fail on 820d5e5ff at about 640 KiB, and the report quotes the base figure. Also test the long-message path (a send whose messages exceed WORDS_BYTES, so the pages are admitted and held) for an unchanged peak.
> 
> 4. The attack case: if no session can reach a raw mux send (beamlet's hub frames what it sends), say so on the page in one sentence: who can send such a transfer, which is any program with a connection, a native among them. Then make the boot case a native program in a session's budget sending the transfer to bootfsd, with the verdict bootfsd's heap record peak. If even a native cannot shape it, the host test is the attack and the page says why.
> 
> Pages: bootfsd.md's residual goes, and serving.md's 'A request' item gains a clause that a send's messages are taken in place, never listed. Tier A, small, red review.

### Implementer · Question

Event: `f9d1ec8fb9eef583db2100b3c804a432` · 2026-10-21T14:17:50Z

> B100 attack case: one finding and one sizing question.
> 
> 1. A session reaches the raw send itself: beamlet's send native takes any words and up to 65,536 bytes (MAX_BUFFER). So tests/session-mux-flood.toml is pure Elixir on image/boot.toml: alice mints her own /boot connection (NinepCommon.new_connection), opens a mux session, and sends 9,362 7-byte messages in one transfer; a second completion call gets OPENED (the first session ended at the 257th). The verdict is the bench's memory scan of bootfsd's heap record. No test program and no recipe change.
> 
> 2. Measured (head / 820d5e5ff):
> - rv32: heap 1,147 / 1,335 pages. The base FAILS: "heap needs 2670 pages for twice its 1335-page peak, capped at 2510". Head passes.
> - rv64: heap 942 / 1,177. Both under cap/2, because bootfsd's cap is sized from rv32's larger boot peak. rv64 shows the gap but can't fail on it.
> - rv64 FAILS on both, on bootfsd's STACK: 8,952 / 9,112 bytes peak, against 4 declared pages (needs 5 for twice the peak). rv32: 7,336 / 7,640, which passes. Pre-existing: the image's stack declarations come from idle and SSH-login boots, and no memory case drove a session's mux traffic plus new_connection at bootfsd before.
> 
> Options for the stack:
> (a) In B100, raise bootfsd's stack_pages 4 → 5 in image/manifest.json, as twice the new largest peak (testbench.md "The memory budget" rule), plus the page's mention if any.
> (b) The case runs rv32 only for the memory verdict, rv64 judged on the session's answer alone (no knob for that I know of), and the stack goes to a follow-up.
> (c) Leave the case rv64-failing and file the stack as a follow-up. Not acceptable for a gate.
> 
> I recommend (a): it's the declaration rule applied to a peak a session can reach, it's one line plus the page, and the case keeps both widths. Note that only rv32 is the heap witness; I'll state that in the case and the report. OK?

### Architect · Answer

Event: `cf0a3c0e3235f1aacdb0f2daf0ea8b83` · 2026-10-21T14:18:00Z

> (a), OK. It is the declaration rule applied to a peak a session can now be shown to reach, and the case keeps both widths. Good finding on both counts.
> 
> 1. The raw send reachable from a session's Elixir is the stronger attack, and it settles condition 4: the page says any session can send such a transfer, through beamlet's send native (up to MAX_BUFFER bytes), so the bound is the server's to keep. That sentence goes on serving.md beside 'taken in place'. A pure-Elixir case on the image's own recipe is the best shape it could have.
> 
> 2. bootfsd's stack: 4 → 5 pages in image/manifest.json, as twice rv64's 8,952-byte peak rounded up (state the arithmetic in the manifest's comment or testbench.md's memory table, wherever bootfsd's row lives). Apply the same arithmetic to every manifest in the tree that declares bootfsd and runs a memory case reaching this path; grep, and list them in the report. Any that don't run such a case keep 4, and the report says why. The memory table's bootfsd row gets the new peak and its source (this case).
> 
> 3. The heap witness: say in the case and on the page that rv32 is the width that can fail on the heap, because the cap is sized from rv32's larger boot peak, and rv64 shows the gap (942 against 1,177) without being able to fail. That's honest and enough. No knob, no rv32-only split.
> 
> Re-run the memory cases that boot bootfsd (userland-boot, init-boot, beamlet-footprint, the B99 set) on both widths for unchanged verdicts. The report quotes the base's rv32 failure line as the attack's red.
