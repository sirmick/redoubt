# Re-homing rv32 onto the unified path

Status: DONE, 2026-09-18. rv32 and rv64 boot on QEMU `virt` through the same Rust firmware
(RustSBI Prototyper), the same loader (loader64), the same SBI/PLIC/timer platform, and the
same physmap paging design — differing only in width (Sv32 vs Sv39). The old rv32-only code
(Precursor, bao1x, VexRiscv, the Sv32 window scheme, prebuilt blobs) is deleted. The whole
test bench is green on both widths (26/26, SMP included).

QEMU here ships no rv32 OpenSBI, so rv32 boots under the RustSBI Prototyper built for
`riscv32imac-unknown-none-elf`; the bench selects it per width (`resolve_firmware`).

## De-risk (done)
RustSBI Prototyper builds for rv32. Every loader dependency (fdt-rs, ed25519-compact,
sbi-rt, tar-no-std, crc, xous) builds for rv32. The only thing that does not is our own
`sv39` crate, which hardcodes 64-bit. So the work is: make paging width-generic, then wire
the loader and kernel to use it on rv32 with the SBI/PLIC path.

## Sv32 vs Sv39
Same low 10 PTE flag bits; PPN starts at bit 10 in both. Differences:

| | Sv32 (rv32) | Sv39 (rv64) |
| --- | --- | --- |
| `usize` | u32 | u64 |
| levels | 2 | 3 |
| entries / table | 1024 | 512 |
| VPN bits / level | 10 | 9 |
| PTE width | 4 B | 8 B |
| leaf sizes | 4 KiB, 4 MiB | 4 KiB, 2 MiB, 1 GiB |
| `satp` mode | 1 << 31 | 8 << 60 |
| `satp` ASID | bits 22..30 | bits 44..59 |
| canonical addrs | all 32 bits | sign-extended at bit 38 |

Because the flag bits and PPN position match, a `usize`-based `Pte` and the flag logic are
identical; only the level count, entries-per-table, VPN shift, and `satp` fields are
width-specific. These become `cfg(target_pointer_width)` constants in one crate.

## Address layout (rv32, Sv32)
rv32 splits user/supervisor at 0x8000_0000. Kernel half is the upper 2 GiB.
- Physmap of RAM: high in the kernel half, `virt = PHYSMAP_BASE + phys`, 4 MiB megapage leaves.
- Fixed kernel/per-process VAs: the top of the 4 GiB space, mirroring the rv64 layout scaled down.
(Exact constants in `xous-rs/src/arch/riscv/mem.rs`, chosen alongside the physmap size.)

## Width bugs found at first boot (all "assumed rv64")
Recorded so the pattern is recognisable next time a width creeps in:
- `PHYSMAP_BASE + phys` is only right when `PHYSMAP_PHYS_BASE == 0`. Use `physmap_virt()`.
- The one loader writes XArg **v2** (64-bit, low word first) and 64-bit MREx entries on both
  widths; the kernel must parse them the same way (through `u64`, not `usize`, to avoid a
  `<< 32` that overflows a 32-bit `usize`). `MemoryRangeExtra` must be `u64`-wide.
- On rv32 the PLIC is at its own root entries, not under the kernel root, so the loader must
  pre-create the shared intermediate tables (`reserve_tables`) before user address spaces
  copy the kernel roots — otherwise the kernel's later PLIC mapping is invisible to them.
- Reading the 64-bit `time` CSR on rv32 needs `rdtimeh`/`rdtime` with a wrap-retry loop.
