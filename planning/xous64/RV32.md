# Re-homing rv32 onto the unified path

Status: in progress, 2026-09-18. Goal: rv32 and rv64 boot on QEMU `virt` through the same
Rust firmware (RustSBI), the same loader, the same SBI/PLIC/timer platform, the same
physmap paging design — differing only in width (Sv32 vs Sv39). Then the old rv32-only
code (Precursor, bao1x, VexRiscv, the Sv32 window scheme, prebuilt blobs) is deleted.

## De-risk (done)
RustSBI Prototyper builds for rv32. Every loader dependency (fdt-rs, ed25519-compact,
sbi-rt, tar-no-std, crc, xous) builds for rv32. The only thing that does not is our own
`sv39` crate, which hardcodes 64-bit. So the work is: make paging width-generic, then wire
the loader and kernel to use it on rv32 with the SBI/PLIC path.

## Sv32 vs Sv39
Same low 10 PTE flag bits; PPN starts at bit 10 in both. Differences:

| | Sv32 (rv32) | Sv39 (rv64) |
| --- | --- | --- |
| `usize` | u32 | u64 |
| levels | 2 | 3 |
| entries / table | 1024 | 512 |
| VPN bits / level | 10 | 9 |
| PTE width | 4 B | 8 B |
| leaf sizes | 4 KiB, 4 MiB | 4 KiB, 2 MiB, 1 GiB |
| `satp` mode | 1 << 31 | 8 << 60 |
| `satp` ASID | bits 22..30 | bits 44..59 |
| canonical addrs | all 32 bits | sign-extended at bit 38 |

Because the flag bits and PPN position match, a `usize`-based `Pte` and the flag logic are
identical; only the level count, entries-per-table, VPN shift, and `satp` fields are
width-specific. These become `cfg(target_pointer_width)` constants in one crate.

## Address layout (rv32, Sv32)
rv32 splits user/supervisor at 0x8000_0000. Kernel half is the upper 2 GiB.
- Physmap of RAM: high in the kernel half, `virt = PHYSMAP_BASE + phys`, 4 MiB megapage leaves.
- Fixed kernel/per-process VAs: the top of the 4 GiB space, mirroring the rv64 layout scaled down.
(Exact constants in `xous-rs/src/arch/riscv/mem.rs`, chosen alongside the physmap size.)
